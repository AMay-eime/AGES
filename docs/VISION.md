# AGES 開発理念

> **All Games should be Edited Speedy.**
> とにかく、ゲーム開発のスピードを上げる。

## 1. なぜ作るのか

AIでゲームを作ることが当たり前になった。それでも、AIと既存のゲームエンジンの組み合わせは遅い。
コンパイル待ち、エディタの更新待ち、GUIでしかできない操作、AIが全体を把握するために大量のファイルを読む時間。
実際に素のHTMLでゲームを作ってみると、コンパイルもエンジンのリフレッシュも要らないので圧倒的にスムーズだった。

AGESは「HTML開発の速さ」と「ゲームエンジンの便利さ（エディタ・パラメータ調整・チームでの作業）」を両立させる。
そして最初から **AIが操作することを前提に** 設計する。既存エンジンにAIを後付けするのではない。

## 2. 何で勝負するのか

機能の数でUnityに並ぶことではない。**AIと人が一緒に作るときの速さ**で既存エンジンを超える。
長期的にはUnityに匹敵するものを目指すが、各段階で実際にゲームが作れる状態を保ちながら育てる。

## 3. 速さを決める2つの指標

| 指標 | 意味 |
| --- | --- |
| **思考時間の短縮** | AIが迷う・推測する・調べ回る時間を減らす |
| **トークンの節約** | AIが読む量・書く量を減らす |

この2つはエディタの存在価値に直結する。新しい機能は必ず「この2つを良くするか、少なくとも悪くしないか」で判断する。
効果は推測ではなくベンチマークで測る（[PLAN.md](PLAN.md) の「ベンチマーク」）。

## 4. 原則

1. **正本はテキスト。** 人はエディタで、AIはCLIで、同じファイルを編集する。どちらから変えても結果は同じ
2. **推測させずに試させる。** 画面なしで数秒で実行でき、毎回同じ結果になる。AIは考え込む代わりに動かして確かめる
3. **必要な分だけ返す。** 地図・要約・差分。全部を読ませない。画像より状態データ
4. **やり方は一つ。** 同じことをする方法が複数あるとAIは毎回迷う
5. **エラーに答えを書く。** 場所・許容範囲・「もしかして」候補。原因探しをさせない
6. **待たせない。** 実行時の外部依存ゼロ、コンパイルなし、変更は即座に反映
7. **人の決定を守る。** 人が調整した値には印を付け、人がロックした値はAIには絶対に変えさせない

## 5. 人とAIの役割

- **面白さの核・手触り・個性を決めるのは人。** AIはそれ以外を速く、正確に、少ないトークンで支える
- AIは人の調整を勝手に上書きしない。変えるべき理由があれば提案する
- 人の編集はすべて記録し、AIが読める形で残す（意図をくみ取るため、編集者同士の行き違いを防ぐため）
- 🔒ロックがあることで、人は安心してAIに大きな作業を任せられる。「ここは触らないで、それ以外は全部やって」と頼める

## 6. やらないこと

- 速さに効かない機能を、既存エンジンにあるからという理由だけで足すこと
- AIのために人の操作を不便にすること（人が直接ファイルやパラメータを編集できることは必須）
- 外部パッケージへの依存を増やすこと（どうしても必要な場合は理由を [DECISIONS.md](DECISIONS.md) に残す）
- 出力を長くすること（AI向けの出力は常に短く）
