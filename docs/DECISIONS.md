## 2026-11-11 AI が文字で空間を確かめる道具（ages space。段階4 の 9）

- **`ages space <dir>`（MCP は ages_space）: 3D の物を1つ1行で、位置・大きさ・何の上にあるか（乗っている・浮いている・沈んでいる）・ゲームのカメラのどこに映るか（画面の外・後ろ・隠れ・見かけの高さ）を出す。** 3D の置き間違いは数字（x y z）を読んでも気づきにくく、画像は読む量が多い。2D の `ages ui`（UI の配置を文字で）と同じ考え方
- ⚠ にするのは、直す必要がほぼ確かなものだけ: ほかの物の面に沈んでいる（どれだけ上げれば乗るかも出す）、当たり判定が見た目からずれている（足元が原点のモデルに offset を書き忘れた、など）。浮いているのはわざとのことが多い（コイン）ので、文で出すだけ
- 外枠（軸にそろった箱）で数える。モデルは要約（`ages assets` と同じ大きさ・中心）で数えるので、モデルを開かない・画面も要らない
- **追加パッケージが命令を持てるようにした**（`PackageDef.cli` と `src/packages/<名前>/cli.ts` の COMMANDS）。CLI の `ages <命令> <dir>` と MCP の道具 `ages_<命令>` の両方になり、**MCP の道具の一覧に出るのは、そのパッケージを入れているプロジェクトだけ**（2D だけのプロジェクトで毎回読む量は 1文字も増えない。テストで確かめる）
- 上・前・横からの小さな画像は作らなかった（文字で足りるかを、見本のゲームを作りながら確かめる。足りなければ足す）

## 2026-11-11 3D の当たり判定（段階4 の 8）

- 形は Collider3D（箱・球・カプセル。回転・倍率つき）。調べるのは `ages/3d` の `hit3`（overlaps・test・point・sphere・box・ray・entered）。**2D の ctx.hit と同じ名前・同じ考え方**（グループの名前で絞る・結果はワールドに入った順）にして、覚えることを増やさない
- **押し返し・重力・壁で止まることは本体に入れない**（開発者の決定）。手順（guide:3d-hit）に、重なりと線だけで書く短い書き方（軸ごとに動かして重なったら戻す・足元へ線を下ろす）を載せ、見本のゲームに同じものを入れる
- 「重なり始め」は、追加パッケージが ctx を広げられないので、部品の値に記録する（`with` のグループ → `touching`・`entered`）。値なので `--watch` で確かめられ、巻き戻し・保存にもそのまま乗る
- 重なりは形どおりに求める（箱どうしは分ける向き 15 本、箱と丸い形は線分と箱の距離）。触れているだけは重なりに数えない。面の上から中へ向かう線は距離 0 で当たる（足元の地面を取りこぼさない）
- `ages check`: Transform3D のない Collider3D、`with` のグループを誰も名乗っていない（名前の間違い）を ⚠ で知らせる
- エディタ: 「3D シーン」に当たり判定の形を緑の線で出す。「＋ 足す」から、選んだ形・モデルに合う大きさで付けられる（モデルは要約の大きさと中心）
- まだ: 三角形の集まり（地形のメッシュ）との当たり、広い場面のための絞り込み（いまは全部を順に調べる。数百個まで）

## 2026-11-11 影（段階4 の 7）

- **影は太陽（sun）の影だけ。何も設定しなくても出る**（置いた物が地面に付いて見えるかどうかは、3D の見た目でいちばん効く。AI が設定を覚えなくてよい）。点の光は影を落とさない（6面ぶん描くので重い。要ると分かってから）
- 仕組みは影の地図1枚（2048 画素）。カメラの見える範囲のうち、手前から `Light3D.shadowRange` m（既定 30）までを囲む。段階に分けた地図（遠くまでくっきり）は作らない: 個人〜小規模の3人称・見下ろしのゲームは 30m で足り、広げたい人は1つの数字を変えればよい
- 影のふちは、まわり9点をならしてやわらかくする。カメラが動いても影のふちが泳がないよう、地図の中心を画素に合わせ、大きさを半径の切り上げで固定する
- 面が自分の影で縞になるのは、描くときに奥へずらす + 比べるときに面の向きへずらす、で防ぐ（調整の数字は出さない。日なたの明るさが影なしと同じになることをテストで確かめる）
- 物ごとに `shadow`（落とすか）を切れる。受けるかどうかは切れない（要ると分かってから）。半分より透ける物は落とさない
- 影の濃さの設定は作らない（影の中は全体の明るさ Environment3D.ambient だけになる。濃さは ambient で決まる）
- ついでに: アセットのパネルで、モデルが字の見本（Aaあ）で出ていたのを直した（🧊 と大きさ、選ぶと三角形の数と動きの一覧）

## 2026-11-11 モデルの動き（骨のアニメーション。段階4 の 6）

- **動きは Model3D の `clip`（動きの名前）を書き換えるだけで再生・切り替えできる。** 別の部品（アニメーター）や状態の図は作らない（いつ何の動きにするかはゲームのコードが決める。AI は `m.clip = 'run'` と1行で書け、人はインスペクタで名前を選べる）。切り替えは、前の動きのその時の姿勢から `fade` 秒（既定 0.15）で混ぜる
- 時刻（`time`）は部品の値として持ち、システム model3d が進める。**画面なしの `ages run` でも同じに進み、`--watch` で確かめられる**（描画は時刻から姿勢を求めるだけで、状態を持たない）。くり返しは長さで折り返し、`loop` が false の動きは最後で止まって `done` が true になる（攻撃の終わりで待機へ戻す合図）
- 動きの長さは、モデルの要約（`ages assets`・地図に「動き: idle(1.2s)」）と同じものを登録簿（`registry.models`）に入れて、エディタ・書き出したゲームにも渡す。ゲームのコードがモデルを開かなくても長さが分かる
- 名前の間違いは「動かないだけ」で気づきにくいので、`ages check` が ⚠ で知らせる（3d-clip。検証が素材の要約を読めるよう、CheckView に `asset(path)` を足した）
- 骨は頂点ごとに4本まで、数に上限なし（骨の行列は画像にして渡す）。鍵の補間は LINEAR・STEP・CUBICSPLINE
- 読めないものははっきり止める: 圧縮されたモデル（Draco・meshopt）は「圧縮なしで書き出して」と出す
- まだ: 骨に物を付ける（手に剣）、表情（モーフ）、2つの動きを重ねる（上半身だけ別の動き）。見本のゲームで要ると分かったものから足す

## 2026-11-11 エディタの「3D シーン」パネル（段階4 の 4）

- **3D を作るための視点は、ゲームのパネルとは別のパネル「3D シーン」にした**（Unity の Scene ビューと Game ビューの分け方）。ゲームのパネル（2D の選ぶ・動かす・UI の配置）に 3D の操作を混ぜると両方が複雑になる。パネルはパッケージの中（src/packages/3d/editor.ts）にあり、入れているプロジェクトのエディタでだけ読み込む（PackageDef.editor）。初めて出すときは中央の前に出す
- 視点は「見ている点のまわりを回る」形。右ドラッグ（Alt+左ドラッグ）で回す・中ボタン（Shift+右ドラッグ）で平行移動・ホイールで寄る／引く・F で選んだ物へ。**この手触り（速さ・ボタンの割り当て）は開発者が触って決める**（いまは仮）
- 2D の物（画像・UI）はこの視点では描かない（3D の物だけの世界を渡す）。地面に 1m の格子（10m ごとに濃く、x の軸は赤・z の軸は青）
- 選ぶ: 光線と、形を囲む箱（球は球）の交わり（pick.ts。ゲームの狙い・当たり判定の問い合わせ・AI の確かめでも使う）。形のない物（光・カメラ・空の物）は印（☀💡🎥◇）で出し、印の近くで選ぶ
- ギズモ: 動かす（世界の軸）・回す（世界の軸のまわり。行列で回してから rx・ry・rz に戻す）・大きさ（物の軸と、真ん中で全体）。W/E/R。Ctrl で刻み（0.5m・15度・0.1倍）。親のある物は、世界で動かしてから親から見た値に直す。ドラッグ中は試しの世界の値を変え、離したときに変わった値だけを1回の編集で保存（元に戻せる。ロックされた物は動かせない）。再生中は見るだけ
- ギズモ・選んだ物の枠・印は、上に重ねた 2D のキャンバスに描く（いつも手前に見える）。格子だけは奥行きを比べて 3D の中に描く
- 「＋ 足す」: 箱・球・円柱・カプセル・板・太陽の光・点の光・カメラ（カメラはいまの視点の位置と向きで）
- 階層のパネルは Transform3D.parent も木にし、ドラッグで親を変えると世界での位置・向き・大きさを保つ（計算は要るときだけ読み込む）
- 確かめ: 画面なしの Chrome に本物のマウス・キーを送って、選ぶ・動かす（保存と元に戻す）・回す（15度刻み）・大きさ・視点・足す。2D のプロジェクトにはパネルが出ない（test/pkg3d-editor.test.ts）

## 2026-11-11 3D の描画: 基本の形・光・2D の下の層（段階4 の 3）

- **3D は 2D の描画の「下の層」として描く**（src/render/layer.ts の窓口。背景を塗った直後・2D の物の前）。2D の描画（webgl.ts）はそのままで、パッケージが層を持っていれば呼ぶだけ。HUD・メニューは今までの UI がそのまま上に重なる
- 3D は自分の描く先（色 + 奥行き、4倍のアンチエイリアス）に描いてから、2D の描く先へ重ねる。2D 側（画面・後処理の描く先）に奥行きの用意がなくてよく、後処理（PostEffect）も 3D ごとかかる。重ねるときに縁がにじまないよう、色に不透明度をかけた形（premultiplied）で持つ
- 空の色は画面の背景の色（view.background）。3D の物がないシーンでは 3D の層は何もしない
- 形は Mesh3D（箱・球・円柱・カプセル・板）。箱などは 1m で作って size で伸ばし、カプセルは丸い所がつぶれないようその大きさで作る。見た目は色・画像・ざらつき・光を受けない・透ける（透ける物は奥から描く）
- 光は 太陽1つ + 点の光8つまで + 全体の明るさ（上からの色と下からの色）。光を1つも置かなければ既定の太陽（真っ暗で何も見えない、を避ける）。太陽の向きは物の前（+Z）
- **光の計算は画面の色のまま行う**（直線の色に直さない）。2D の色・エディタの色の欄と同じ色に見えることを優先した。glTF の見た目を正確に合わせる必要が出たら見直す
- 検証: Transform3D のない Mesh3D・Camera3D・Light3D を ⚠（パッケージが検証を持てるようにした）
- 確かめ: 画面なしの Chrome で撮った画像の点の色（光を受けない球・床・空・上に重なる 2D の UI・光を受けた箱）。エディタのゲームの画面にも、そのまま出る（編集中も）

## 2026-11-11 3D の位置・回転・親子とカメラ（段階4 の 2）

- 開発者の了承: 3D の残り（2〜10）は、テストが通ったものを AI の判断で順に取り込み、区切りで報告する。4（エディタの3D操作）の後は必ず止めて、開発者が触る
- 座標は glTF・three.js と同じ（右手系・Y が上・単位は m）。物の前は +Z、カメラが見る向きは −Z。AI がよく知っている決まりに合わせ、モデル（glTF）を回さずに置けるようにするため
- 回転は度で3つの数（rx・ry・rz）。順番は ry（左右）→ rx（上下）→ rz（傾き）＝ R = Ry·Rx·Rz。ゲームのカメラとキャラクターは「左右を向いてから上下」が自然なため（three.js の既定 XYZ とは違うので、手順に書いた）。クォータニオンはデータに出さない（人と AI が数で読み書きしにくい）
- Transform3D は 2D の Transform と別の部品（x・y・z・rx・ry・rz・sx・sy・sz・parent）。2D の Transform に z を足さないのは、2D のプロジェクトの欄・地図を増やさないため。位置は 2D と同じく1つずつの数（住所で1つだけ変えられる）
- 計算（行列・回転）は自前（src/packages/3d/math.ts。外部のパッケージなし）。行列はふつうの数の配列（Node でもブラウザでも同じ結果。描くときだけ Float32Array にする）
- カメラは Transform3D + Camera3D。追いかけ（follow・offset・lag・look）だけを標準にし、回り込むカメラなどはゲームのコードで書く。世界 → 画面（toScreen）と 画面 → 光線（screenRay）は、描画・エディタのクリック・AI の確かめで同じものを使う
- 本体に足したもの: フィールドの型 `vec3`（[x, y, z]。インスペクタ・検証・CSV・トゥイーン）。親が消えたら子も消す決まりを Transform3D.parent にも（world.ts。名前で見るだけで、パッケージは import しない）
- パッケージの部品は、地図・ages find で標準の部品と同じ扱い（地図に全部の欄を並べない）

## 2026-11-11 追加パッケージの仕組み（段階4 の 1。PLAN 76）

- 開発者の決定: 3D は「ダウンロードはされるが、入れていないプロジェクトでは読まない」という棲み分けでよい。当たり判定は重なりと光線の問い合わせまでを作り、押し返し・重力・キャラクターが壁で止まる処理は作らない（見本のゲームのコードとして簡単なものを書き、使う人の手本にする）
- **追加パッケージは本体と同じリポジトリの `src/packages/<名前>/` に置き、プロジェクトが `ages.project.json` の `packages` に書いたときだけ読み込む。** 別のリポジトリにしないのは、本体と版がずれず、入れる手間（取ってくる・版を合わせる）が増えないため。`src/` の下なのは、エディタのサーバーが `src/` をそのまま配っていて、本体への相対 import が Node でもブラウザでも同じに通るため
- 入れるかを設定（packages）で決めるのは、コードを読み込まなくても全部の道具（CLI・エディタ・書き出し・MCP）が分かるため。「import したら入る」形は、1つのプロセスが複数のプロジェクトを扱うとき（MCP・テスト）に、2D のプロジェクトにも 3D が入ってしまうのでやめた
- 入れていないプロジェクトに足さないもの: 部品・システム・表（登録簿）、地図の行、手順（guide）の項目、書き出しのファイル。AGENTS.md には「追加パッケージがある」の1行だけ足した（AI が 3D の存在を知る入口。中身は guide:packages）。2D の地図・道具の定義の文字数は変わらない（test/budget.test.ts・test/packages.test.ts）
- 入れたプロジェクトでは: 地図の先頭に `## package 3d` とその機能の目次（AGENTS.md の目次と同じ書き方）、`guide:項目` でパッケージの GUIDE.md、ゲームのコードから `import … from 'ages/3d'`。パッケージの部品は標準と同じ扱い（ゲームで同じ名前は作れない）、システムはゲームの後・本体の標準の前
- 読み込みの行き先は式で組み立てる（`./${名前}/index.ts`）。書き出しは import をたどって本体を写すので、文字で書くと使っていないパッケージまで写ってしまう。使うものは export.ts が名前で足す
- 間違いの知らせ: 知らない名前（使える名前つき）、packages に書かずに `ages/3d` を import（ages check）、入れていないパッケージの手順を引いた（入れ方つき）

## 2026-11-11 段階5: 人と AI の共同作業の見える化（PLAN 75）

- 開発者の要望: 「エディタ内で AI とのやり取りができればできるほどよい」。案の 1〜5 を、AI の変更を一目で → いまの作業 → 質問と付箋 → ぶつかり防止 の順で作った
- **やり取りは `.ages/talk.jsonl`（追記だけ・Git で共有・統合では両方の行を残す）**。AI と人が別の端末（AI はクラウド、人は手元）でも、Git を通して付箋・質問が届く。中身: AI の作業（題・段階・触る予定の住所）・AI の質問（選択肢・住所）と人の答え・人の付箋（住所）と AI の返事・取り下げ
- AI の道具は `ages talk`（MCP は `ages_talk` の1つ）。作業の始めに `--task`（`--steps` `--touch`）、区切りで `--step`、終わりに `--done`、人が決めることは `--ask`（答えを待たずに続ける）、付箋は `--reply ID` で済にする。引数なしで人の書き込みを読む。道具を1つにしたのは、毎回読む道具の定義を増やしすぎないため
- **AI が読んでいない人の書き込みは、ほかのすべての ages の出力（MCP も）の先頭に1行**（`📌 エディタの人から: 付箋 1・答え 1（ages talk で読む）`）。AI は話しかけられたときにしか動かないので、待ち受けの代わりに、作業の中の次の命令で必ず気づくようにした。読んだ所は `.ages/talk-cursor`（共有しない）
- 作業中の AI の変更（操作ログ）には作業の ID（task）を付ける。エディタは作業ごとにまとめ、✓ 見た・↶ 戻す（新しい順。後で変えられた所があれば止まる）ができる。人が ↶ で戻した値は ★（人が決めた値）になる
- 確かめたかは人ごと・端末ごとなので AGES_HOME に置く（Git では共有しない）。「すべて見た」はその時刻までを全部
- コードなどのファイル（.ts・.md・シェーダー・ages.project.json）は、エディタのサーバーが起動時に中身を覚え、外で変わったら行の差分を残す。誰が変えたかはファイルからは分からないので、AI が作業中ならその作業のものとし、そうでなければ「作業を伝えずにした変更」。コードは ↶ では戻さない（差分を見るだけ）。差分は手作り（同じ先頭と末尾を外して比べる。外部のパッケージは使わない）
- 印: パネルは `data-ai="住所"` を書くだけで、AI が変えて確かめていない（左に色の線・来たばかりは光る）・AI が触る予定（物と外側だけ。中の欄すべてに付けると見分けにくい）・付箋（📌）が付く。描き直しでは足された要素だけを塗り、AI の変化で全部を塗り直す（ゲームの表示など細かく変わる所で重くならないように）
- ぶつかり防止: 人がインスペクタ・表の欄に入力している間（最後に打ってから 20 秒）は、AI はその欄と、それを含む物・部品を変えられない（「人がエディタで … を入力中です」）。AI が触る予定の所に人が入力を始めたら知らせる
- 毎回読む量の上限を上げた（道具 6500 → 7200・説明 1100 → 1200・AGENTS.md 3900 → 4250）。人と同時に作業するための最小の手順で、AI が作業を見せないと見える化が働かないため
- 確かめ: 画面なしの Chrome で、作業が上に出る・印・✓・↶・質問に答える・付箋が AI に届く・差分・入力中の欄を AI が変えられない、を通した（test/ai-talk.test.ts）。操作ログ 6 万行を読むのは約 90ms（変化のたびに読み直してよい）

## 2026-11-10 ゲームの画面の取っ手: 移動・回転・拡大縮小（PLAN 68）

## 2026-11-10 エディタが GitHub から自動で取り込む（PLAN 57）

- 開発者の決定: 自動の取り込みを作る。**手元にプッシュしていない変更がある場合は、プッシュしてから取り込むかを聞く**

## 2026-11-09 段階2-15 エディタ拡張の API（開発者と相談）・プレハブの派生

エディタ拡張の API（開発者の回答）:
- **書き方は1つにまとめる**: `defineExtension` 1つに、パネル・インスペクタの欄・メニュー・描き込みなどを要る分だけ書く。地図には拡張ごとに1行（名前・説明・変える値・使う窓口）。今の `defineWindow` はそのまま使える（パネルだけの拡張の短い書き方）
- **本体の残りの機能（試しの窓・格子への吸着・複数選択など）も、拡張と同じ API の上で作る。** API が足りているかを確かめられ、AI が真似できる手本にもなる
- **最初に用意する窓口はインスペクタの欄の見せ方**（と通知）。ほかの窓口（ゲームの画面への描き込み・取っ手・右クリックのメニュー）は、それを使う本体の機能を作るときに API として足す
- これまでの決まりは変えない: 値を変えるのは `api.patch` だけ、`edits` の外と🔒は変えられない、拡張は隔離しない
- 相談の間に、API と関係しない派生を先に作る（開発者の了承）

プレハブの派生:
- **ファイルには元の名前・変えた値・外した部品だけを書き、使うときに元と重ねる。** 元の値を写すと、元を直したときに派生の数だけ直すことになり、人もAIも手間とトークンがかかるため（Unity の Prefab Variant と同じ考え）
- **重ね方はフィールドごと**（リスト・構造体は丸ごと）。フィールドより細かく重ねると、どの値がどこから来たかが分かりにくくなるため
- **どの操作も、派生では元と重ねた写しの上で行い、終わってから「変えたフィールドだけ」を書き戻す。** 操作ごとに派生の場合を書かずに済み、これから足す操作もそのまま派生に使える
- **元と同じ値にしたフィールドは「受け継ぐ」に戻す。** 場所の変更・名前の変更で参照が直ったときに、受け継いでいた値が勝手に「変えた値」にならないため。戻すための `revert` も用意した（派生でない物では既定値に戻す）
- **元の変更で派生の受け継いだ値が変わるときも、変更の一覧に入れる**（via）。受け継いだ値にロックを付けたら、元を変えてもそのロックは守られる
- **プレハブを作る・消す・名前を変える操作を用意した**（これまで op がなく、ファイルを直接作るしかなかった）。名前を変えると、既定値で指している所（Spawner.prefab の既定 "enemy" など）にも新しい名前を書く。コードの `spawn('名前')`・`sound.play('名前')` は検証に入れ、消すときは止め、名前を変えるときは ⚠ で知らせる（コードは直さない。シーンと同じ）
- `copy` は派生にしない写し（中身をまるごと）。似た物を作るときは、写すより派生を勧める（guide:prefab）

## 2026-11-09 段階2-11 UIの土台

- **UI はシーンに置く物（標準の UI コンポーネント）にする。コードで画面を組み立てる形（即時モード）にはしない。** 人がエディタで配置を直し、★・🔒 で守れるようにするため。AI も patch の住所で直せる

- サンプルの見た目（ゲージの色・ボタンの色）は仮

## 2026-11-09 段階2-10 シェーダー

- **シェーダーのファイルは、関数 `effect` 1つと値の宣言だけ。** `#version`・`main`・頂点のシェーダー・テクスチャの受け渡しは AGES が包む。AI が書く量と間違える所を減らし、地図に1行で載せるため
- **値の範囲・既定値・説明は、uniform の行の終わりのコメントに書く。** 別のファイル（JSON など）に分けると、シェーダーと宣言がずれる。1か所に書けば、エディタの欄・検証・地図・トゥイーンが全部そこから作れる
- **値は物のコンポーネント（Effect / PostEffect の params）に置き、ゲームの状態として扱う。** トゥイーン・★・🔒・元に戻す・検証が、他の値とまったく同じに使える。住所は `…Effect.params.名前`（選んだシェーダーで中身の形が決まる型 `params`）

- **標準のシェーダーを6つ用意する**（光らせる・縁取り・溶かす・色を抜く・端を暗く・ブラウン管ふう）。よく使う効果はファイルを書かずに済み、中身は新しく書くときの手本になる
- サンプルの効果（被弾で白く光る・画面の端を暗く）の手触りは仮。どう見せるかは人が決める
- **できないことは、使用者が「やろうと思えばできる」状態ならよい**（開発者）。1つの物に効果は1つだが、重ねたい効果は1つのシェーダーにまとめて書ける。後処理をカメラごとに分ける道（`PostEffect.camera`）は足した（UI のカメラにかけない・分割画面の片方だけ）

## 2026-11-09 段階2-9 演出の基本（トゥイーンとパーティクル）

- **トゥイーンはゲームのロジックの側で、フレームで数える。** 値が変わるのはゲームの状態そのもの（当たり判定や得点の文字にも効く）なので、同じ入力なら同じ結果になり、AI が画面なしで確かめられるようにするため。進行中のものも hash と保存に入れる
- **手触り（秒数・ease・くり返し）は標準の表 `$tweens` に置き、コードは名前で使う。** 手触りは人が決めるもので、表なら人が調整・🔒でき、AI はコードを変えずに済む（音の調整値をプレハブに置くのと同じ考え）。その場の上書きもできる
- **パーティクルの粒は描く側で、実時間と描く側の乱数で動かす。** 何百もの粒をロジックで動かすと、遅く・hash が重くなるうえ、見た目のためにゲームの結果が変わってしまう。ロジックは「いつ・どこで・いくつ」だけを決め、その回数は `ages run` に出す（音と同じ分け方）
- 物が消えても粒は寿命まで残す（爆発の後片付けで粒が途中で消えないように）
- サンプルの手触り（hitFlash・scorePop）は仮。どう感じさせるかは人が決める

## 2026-11-09 ロックを「かける」のはエディタからも

- **人はエディタからもロックをかけられる。外す・ロックされた値を変えるのはロックマネージャーからだけ**（開発者の提案）。かけるのは安全側の操作（AI の自由が減るだけ）で、開発が進む操作なので小気味よく。🔓 を押すとすぐかかり、コンポーネント・表の行ごとにまとめてもかけられる。押し間違えたときは、お知らせのリンクからロックマネージャーで外す
- AI（CLI・MCP）と独自のウインドウからはかけられない（サーバーが断る）。拡張のコードはエディタと同じページで動くので、わざと書けばかけられてしまうが、かけるのは AI 自身を縛る方向にしか働かず、外すのはロックマネージャーからだけなので、ロックを越える道にはならない

## 2026-11-09 段階2-8 元に戻す・やり直し

- **戻す単位は1回の編集（1回の patch・取り込み・テキストの保存）。操作ログの行にその ID（tx）を付ける。** AI は `ages undo` で、逆の操作を考えずに自分の間違いを戻せる（トークンと往復が減る）
- **戻すための中身（変わった文書の前と後、消したファイルの控え）は、この端末の使用者のフォルダに置く**（Git では共有しない。大きくなり、端末ごとの作業の記録なので）。操作ログは共有のまま
- **戻すときは「今・編集の後・編集の前」の3つを見比べる。** 文書ごと丸ごと戻すと、その後の別の人の編集を消してしまうため。同じ所がその後で変わっていたら戻さずに知らせる（黙って上書きしない）。物・行・コマは ID で突き合わせる
- **名前の変更・場所の変更だけの編集は、逆の操作で戻す。** 参照・ロック・★の付け替えを、ふつうの編集と同じ仕組みに任せるため
- **ふつうに戻せるのは自分の編集だけ**（人ごと・AI ごと）。ほかの人や AI の編集は、操作ログから選んで戻す。人が AI の変更を見て戻す使い方を想定
- ロック・★の決まりはふつうの編集と同じ（戻す操作で、ロックを越えられないように）。ただし AI が自分の編集を戻すときは、★の確認は要らない（前の値に戻るだけなので）
- ロックマネージャーでの編集は、エディタの「元に戻す」の対象にしない（エディタからはロックされた値を変えられないため）

## 2026-11-09 ロックマネージャー

- **ロックの操作（付ける・外す・ロックされた値を変える・記録の承認と復元）は、ロックマネージャーからだけにする**（開発者の提案。→ 同日に変更: かけるのはエディタからも）。エディタとは別のポートで開く別のオリジンにし、サーバーはブラウザが付ける送り元（Origin）を見て、ロックマネージャーからの依頼しか受け付けない。エディタの画面や独自のウインドウ（AI が書くコード）からは、ロックを越えられない
- **エディタの側からは、人の手でもロックされた値を変えられない**（開発者の提案。人にとっても心理的に頑健）。エディタの 🔒 は、その値を開いた状態でロックマネージャーを開くボタンにした。エディタのテキストでロックされた値を書き換えても元に戻る
- ただし、人がエディタで行う名前の変更・場所の変更は通す（ロックの住所と値が付いて動き、値の意味は変わらないため）。ロックされたものを消す・ロックされたファイルを動かすのは、外してから
- **ロックされた値の表示・非表示は、人が設定で選べる。既定は表示する**（開発者の決定）。表示しても見るだけ
- **ファイルそのもののロックを足した**（`file:<場所>`）。ロックの値は中身のハッシュ。中身の控えは**この端末の使用者のフォルダにだけ**取る（開発者の決定。Git で共有するとリポジトリが重くなるため）。書き換え・削除は控えから戻し、控えのない端末では知らせるだけ
- ~~Git パネルのプルで届いたロックの変更は、自動で承認する~~ → 変更: **自動では承認しない**。エディタの側からロックの記録を封印できる道を残さないため。プルの後にロックマネージャーを開いて知らせる
- 限界は記録しておく: AI が端末のシェルから、送り元を偽ってロックマネージャーのサーバーを直接呼ぶことは防げない（封印の鍵を書き換えるのと同じ「わざと」の書き換え。完全に防ぐには OS の権限で分ける）

## 2026-11-09 段階2-7 シーン

- **切り替えはゲームのコードから `ctx.scene.goto`。そのフレームの終わりに切り替え、フェードもフレームで数える。** 同じ入力なら毎回同じ結果になり、`ages run` で確かめられる。フェードの見た目は描く側（ロジックは「どこまで進んだか」を持つだけ）
- **切り替えても残す物は tag `keep`（Unity の DontDestroyOnLoad に当たる）。次のシーンに同じ ID があれば、残したほうを使う。** BGM や、シーンをまたぐ状態を持つ物を、特別な仕組みなしで扱える
- **システムはゲーム全体で1つの並びのまま、`scenes` で動くシーンを絞る。`start` はシーンに入るたび、`exit` は出る前。** シーンごとにシステムの並びを持たせると、地図と読み方が増えるため
- **シーンの出し入れは差分編集の操作にする**（addScene / removeScene / renameScene / setScene）。ファイルを直接作ると、開始シーン・参照・ロックが黙って壊れるため。値でシーンを指すための `scene` 型を足した（ステージの表など）
- **コードの中の `goto('名前')` も見る。** AI がシーンの名前を間違えると実行するまで分からないため、`ages check` で知らせる
- **事前読み込みは自動で決める（シーンごとの読み込みの一覧は書かせない）。** 最初にプレハブ・表・コードが使うもの（どこからでも出せるため）と最初のシーンの物、シーンに入る前にそのシーンの物。読み込みの間はフレームを進めないので、結果は変わらない。読み込んだものを捨てる仕組みは、大きなゲームで要るようになってから
- 重ねて読み込むシーン（additive）は作らない。止めたときのメニューなどは、プレハブを出すか UI の段階で考える
- エディタは、再生中にシーンが切り替わるとそのシーンを見せ、止めると始めたシーンに戻る（Unity と同じ）
- **フレームの間に押して離した短い押しも、1フレームは押したことにする。** 取りこぼすと、人が「押したのに反応しない」と感じるため

## 2026-11-09 段階2-6 アセット

- **取り込みは「プロジェクトの中にファイルを置くだけ」のままにする（Unity の .meta のような管理ファイルは作らない）。** AI はファイルを置けば使え、人とAIで手順が同じ。決まった置き場所（scenes/ など）には置けないようにした

- **使われているものは消せない。** 表の行と同じ考え。使っている所の一覧を出す
- **コードの中で場所を文字列で書いているものも探す。** 消すのは止め、場所の変更では ⚠ で知らせる（コードは直さない）。コードを書き換えるのは人かAIの判断にする
- **AI は、ロックされた値や切り方に関わるアセットを動かせない。人が動かすとロックと★が付いていく。** ロックを AI の経路から動かさないため（CLAUDE.md の決まり）
- **拡張子は変えられない。** 名前を変えても中身の形式は変わらないので、壊れたファイルになるため
- **取り込み・差し替えも操作ログに残す。** AI が「人が画像を足した・差し替えた」と分かるように
- **一覧はフォルダごとにまとめ、場所を繰り返さない。地図では使っていないものに「未使用」とだけ付ける。** アセットが多くてもトークンが増えすぎないように。使っている所は `ages assets --refs` で必要なときだけ
- **エディタではアセットをゲームの画面へ落とすと物を置ける**（画像は Sprite、音は Sound、フォントは Text）。人が置くのを速くするため
- 音の長さは WAV に加えて OGG・MP3・M4A もファイルの情報から読む（全体を読まない）。AI が音を聞かずに長さを知れるように

## 2026-11-08 段階2-5 入力

- **キーボード・マウス・タッチ・ゲームパッドを、同じ「ボタンの名前」と「軸の値」にそろえてからゲームへ渡す。** ゲームの側は機器を知らない。1フレームの入力（ボタン・軸・位置・ホイール・指）だけを扱うので、記録と再生がそのまま使え、画面なしの実行でも同じ結果になる。エディタで記録した入力を `ages run --input` で流すと hash まで一致することを確かめた
- **ゲームのコードは「操作の名前」で読み、名前と既定の割り当ては標準の表 `$actions` に置く。** 表にしたので、エディタの表・インスペクタ・操作ログ・★・🔒・検証・CSV がそのまま使える。1つの操作に複数のキーはリストで持つ（データの型を先に作った理由）

- **変えた割り当ては表を書き換えない（実行中だけの上書き）。** 表は人とAIが決める既定値で、プレイヤーの好みとは別のもの。保存は段階2の「セーブ」で `exportBindings()` を入れる
- **マウス・タッチの位置は「設計の大きさで数えた画面の座標」（ctx.view と同じ）。** 画面の大きさや合わせ方が違っても同じ値になり、記録がどの画面でも同じに再生できる。ワールドの座標は `ctx.pointerWorld()` で、カメラの計算も同じ大きさで行う
- **軸の値は 1/256 にそろえ、スティックのわずかなぶれ（0.05 未満）は 0 にする。** 記録が短くなり、再生でずれない。遊びの調整（deadzone）は表の列で人が決める
- **AI の試し実行は操作の名前で書ける（`--keys "0-300:@fire;0-120:@move_x=-1"`）。** キーの割り当てを読まなくてよく、人が割り当てを変えてもAIの確かめ方が変わらない
- **エディタで再生中（一時停止していない・カメラの視点）は、ゲームの画面のクリックをゲームに渡す。** 選ぶのは一時停止中か自由な視点で。マウスで遊ぶゲームを試すときに、クリックのたびに選択が変わらないように
- **割り当ての欄は「押して決める」で入れられる。** キーの名前（KeyboardEvent.code やパッドの番号）を人が覚えなくてよい。名前の間違いは検証で「もしかして」付きで知らせる
- 人に見せる名前では、ゲームパッドのボタンに「パッド」を付ける（キーボードの Y とパッドの Y を見分けるため）

## 2026-11-08 段階2-4 データの型と表

- **型に list（リスト）・struct（構造体）・oneOf（どれか1つ）を足し、入れ子にできるようにする**（開発者の決定）。何を入れるかは、AGESを使うAIがエディタ計画書で使用者と決める
- **どれか1つの値は { kind: 種類, ...中身 }。** JSON でそのまま読め、AIが種類を間違えると「もしかして」で直せる
- **入れ子の中も住所で直接指す（リストは [番号]、構造体は .名前）。リストは insert / removeItem / moveItem で足す・消す・動かす。** 全体を送り直さないのでトークンが少なく、操作ログも細かく残る
- **リストの中の要素は、番号ではロックしない。** 足す・消す・並べ替えで番号が動き、別の値にロックが付いてしまうため。ロックはリスト全体か、構造体の中の項目。人がリストの中を変えたらリスト全体に★
- **表は新しい種類の文書にする（形はゲームのコードの defineTable、中身は data/<名前>.table.json に1行1行）。** 武器・敵・カードのような「同じ形の行がたくさん」は、プレハブやリストより表のほうが人にもAIにも扱いやすく、表計算ソフトとも行き来できる。題材のゲームもデータは CSV の表で持っている
- **表の行には ID を持たせ、住所は $表.行.列 にする。** 並べ替えても住所が変わらないので、セルごとの🔒・★が安全に付けられる
- **ID を変えると、その行を指している値（row 型）も自動で直す。指されている行は消せない。** 黙って壊れた参照ができないように。自動で直した値には★を付けない
- **ゲームのコードからは表を読むだけ（変えられない）。** 表は設計のデータで、実行中の状態は物（エンティティ）が持つ。読むだけにすると、同じ入力で毎回同じ結果になることも守れる
- **CSV の読み込みは「表をまるごと置き換える」。値が同じセルは触らない。** 表計算ソフトの側を正本にして作業する人に合わせる。ロック・★・操作ログが余計に動かないように

- **エディタの音量・ミュートは手元だけ（ブラウザに記憶）。** 作業中の都合で、プロジェクトの音量（人が決めた値）を変えないように
- **サンプルの音は自作の仮の音（作るスクリプトも同梱）。** 外の素材の使い方の決まりを気にせず公開できる。本物のゲームの音は人が決める

## 2026-11-08 段階2-2 カメラ

- **カメラは標準の部品（Camera）にし、位置と回転は Transform を使う。** ほかの物と同じようにクリックで選び、ドラッグで動かし、🔒・★も同じように効く
- **Camera を置かなければ、今まで通り画面全体をそのまま映す。** 小さなゲームはカメラを考えなくてよい
- **追いかけ・範囲の制限・揺れは標準のシステムで行い、ゲームのシステムの後に動かす。** そのフレームで動いた相手に追いつく。AIが毎回書かなくてよい（トークンの節約）
- **揺れはゲームの乱数を使わず、フレーム番号とカメラのIDから決まる値で揺らす。** 見た目のためにゲームの結果（再現性・ハッシュ）が変わらないように。強さは「trauma（0〜1）の2乗」で、重ねると強くなり時間で収まる（よく使われるやり方）
- **見せる範囲の制限は、ゲームの設計の大きさで計算する。** 画面の大きさ（expand で広く見せる場合など）でゲームの結果が変わらないように
- **複数のカメラは depth の順に描き、画面の中の範囲（割合）と映す層の範囲で分ける。** 分割画面・小窓・UI用のカメラが同じ仕組みでできる
- **画面の大きさへの合わせ方（view.fit）は5通り（contain / cover / stretch / expand / pixel）。** 既定は今まで通りの contain
- **エディタには「自由な視点」を付ける。** カメラが動くゲームでは、カメラの外にあるものも見て、選んで、動かせないと作れないため（本来は段階2の最後の「シーンの編集操作」だが、拡大・移動だけ先に入れた）
- **エディタで合わせ方を切り替えても、試しに見るだけにする。** 決めるのは ages.project.json（人が決めることを、画面の操作で黙って変えない）

## 2026-11-08 画像の切り方（スプライトエディタ）

- **格子に並んでいない画像も切れるようにする。Unity のスプライトエディタと同じく、コマの矩形を自由に決められ、人もAIも編集できる**（開発者の要望）
- **切り方は2つの形: 格子（`frame`）と自由な矩形（`frames`。名前・矩形・基準点）。** 格子は短く書けるので残す。エディタで格子のまま手を加えなければ格子で保存する
- **コマは番号でも名前でも指定できる。名前を勧める。** 番号は切り直すとずれるが、名前はずれない
- **切り直しても、前とほぼ同じ場所のコマは名前と基準点を引き継ぐ**（Unity の「Smart」に当たる）。番号がずれた指定は自動で名前に直し、無くなるコマを使っていたら保存しない。黙って別の絵を指すことがないように
- **切り方の変更も差分編集を通す（操作ログ・★・🔒・外部編集の検出）。** シーンやプレハブの値と同じ約束にして、覚えることを増やさない。住所は `sheet:<画像>`。🔒は画像ごと（コマごとにすると、1枚の絵の切り方の中で人とAIの決めたものが混ざって分かりにくいため）
- **自動で直した参照（コマの名前の変更・番号のずれ）には★を付けない。** 人がその値を選んだわけではないため。🔒は効く（ロックした値が連動して変わる操作は、AIからは止める）
- **AIの「自動で切る」は Node で PNG を読んで行う（依存ゼロの読み込みを自作）。** AIが画像を見なくても切れ、結果は文字で確かめられる（トークンが安い）。PNG 以外はエディタで切る
- **`.sheet.json` は1行1コマで書き出す。** Gitの統合がコマ単位になり、人が開いても並びが分かる

## 2026-11-08 段階2-1 描画（WebGL2）

- **位置・画像・図形・文字・アニメーションは「標準の部品」として本体が持つ。** どのゲームでも使うので、プロジェクトごとに作り直させない（AIのトークンも減る）。ゲーム側で同じ名前を作るとエラーにする（どちらが使われるか迷わないように）
- **画像はプロジェクトの中のパスでそのまま参照する。** 取り込みの手順や別の管理表を作らない。ファイルを置けば使え、Gitでもそのまま共有できる
- **スプライトシートは画像の隣の `<画像名>.sheet.json` で定義する。** 画像と対で見つかり、AIは画像を開かずに中身（コマ数・動きの名前）を地図から知れる
- **Animator は標準のシステムで動かし、ゲームのシステムの後に実行する。** ゲーム側が同じフレームで切り替えた動きがすぐ反映されるように
- **値を検証エラーのある状態にする編集は拒否する**（これまでは警告だけだった）。ないファイル・範囲外のコマ・ない動きの名前をAIが入れても、ファイルは壊れない
- **描画とクリックでの選択は同じ形の計算（geom.ts）を使う。** 回転・倍率込みで「見えている形どおりに選べる」ようにするため
- **重なっているものは、同じ場所（4px以内）をもう一度クリックすると奥へ。** 選び方を覚えなくてよく、クリックだけで完結する（開発者の要望「クリックするだけで選択」）
- **何も描かれていないもの（空の文字など）は、編集中だけ◇の印でクリックできるようにする。** 階層から探さなくても画面上で選べるように
- **エディタの状態表示（編集中・重なり 1/2 など）はゲーム画面の外の帯に出す。** ゲームの HUD と重ならないように
- **サンプルの絵は Kenney の Pixel Shmup（CC0）を使う。** 公開リポジトリに置けて、出典の表示も不要なため（ライセンスの文書は同梱）

## 2026-11-08 段階2の範囲と順番

- **段階2は「あまねくゲームを作るのに最低限の要素」だけを本体に入れる。** 題材のゲームは一例で、そのゲームに必要なものをすべてAGESに盛り込む必要はない。参考にしたのは2つの題材（2Dシューティングと、探索型の放置ゲーム）（開発者の決定）
- **2Dのみ**（開発者の確認）
- **データの型として、リスト・構造体・どれか1つ（種類によって中身が変わる型）を入れる。** これがないとAIも操作しにくい。リストに何を入れるかは、企画を受けてAGESを使うAIに決めてもらう（開発者の決定）
- **命令の列（タイムライン）は本体に入れない。** すべてのゲームに必要ではないため。ただし上のデータの型があれば「種類つき構造体のリスト」として表せる。テストに必要な追加部品は作る（開発者の了承）
- **シーン上のオブジェクトはクリックするだけで選べるようにする。** 人が操作しやすいように（開発者の要望）。重なっていれば、同じ場所をもう一度クリックすると奥のものを選ぶ
- **描画をCanvas 2DからWebGL2に切り替える。** シェーダーに必要で、大量の画像を描く速さのため。依存ゼロのまま自作する
- 順番: 描画 → カメラ → 音 → 入力 → アセット → シーン → データの型と表 → 元に戻す → 演出 → シェーダー → UI → 当たり判定 → セーブ → 多言語 → 残りのエディタ機能（開発者の了承）
- **物理演算は依存ゼロとし、AGES本体にも追加部品にも入れない。** 必要なゲームでは、AGESを使うAIがそのプロジェクトの中で作る。本体は当たり判定の土台（円・矩形の判定と範囲の検索）まで（開発者の決定）
- **Gitパネルから人がプルして届いたロックの変更は、一覧で知らせて自動で承認する。** 人が自分の操作で取り込んだものなので、確認を挟まなくても安全性は落ちない。チームで使うときに確認が頻発しないように（開発者の了承）

## 2026-11-08 ロックの封印とMCPサーバー

- **ロックの記録の改ざん対策は「封印」にする。** 人がロックを設定・解除するたびに、プロジェクトの外の鍵で封印し、控えもプロジェクトの外に残す。封印と合わない記録ではAIの編集をすべて止め、控えのロックを効かせ続ける。人がエディタで「承認」か「前の状態に戻す」を選ぶ
- 理由: ロックは「AIが必ず操作できない」ことが価値（開発者の要望）。ロックの記録そのものを書き換える抜け道を、黙っては通れないようにするため
- 封印は端末ごとでGitで共有しない。チームで共有したロックは各自の端末で一度承認する（他人の端末の鍵では検証できないため）
- 限界は文書に明記する（使用者のフォルダの鍵まで書き換えられれば作り直せる。完全に防ぐにはOSの権限で分ける）
- **MCPサーバーを作った。** CLIの関数をそのまま包み、初期化の返事で使い方の説明を渡す。依存ゼロ。`ages init` が `.mcp.json` を作るので、プロジェクトを開けば自動でつながる

## 2026-11-08 ゲームより先にエディタを決める

- **エディタのコンセプトとして、ゲームの企画提案を受けたら、まず「そのゲームを作るにはどんなエディタが必要か」を使用者と確認する。** このエディタを手にしたAIが最初の最初でつまずかないよう、明示する（開発者の決定）
- 実装の決定:
  - `AGENTS.md` の先頭を「ゲームの企画を受けたら（最初の最初に必ず）」にする
  - `ages init` で新しいプロジェクトを作ると、`AGENTS.md`（本体から写す）・`CLAUDE.md`・`EDITOR-PLAN.md`（エディタ計画書のひな形）が入る。プロジェクトだけを開いたAIも、AGES本体を読まずに手順にたどり着ける
  - エディタ計画書には、AIが使用者に確認する質問（調整する値・表や行列・独自ウインドウ・試し方・ロック・作業する人・AGESに足りない機能・作る順番）を並べ、使用者が「合意」にチェックするまでゲームのコードを書かない
  - `ages map`（AIが毎回最初に読む）は、計画書がない・未合意のときに先頭で警告する
  - AGESに足りない機能（画像・音・物理など）は、計画の段階で使用者に伝える

## 2026-11-08 MCPについて

- MCPは「AIが使える道具（関数）と、その説明書を、AIのアプリに渡すための決まりごと」。MCPサーバーは、ネット上に借りるサーバーではなく、使用者のPC上でAIのアプリが起動する小さなプログラム（標準入出力でやりとりする）
- 使い方の説明そのものは、MCPがなくても `AGENTS.md`・`CLAUDE.md`・`ages help`・`ages map` で渡せている。コマンドを実行できるAI（Claude Codeなど）ならCLIで十分
- MCPが効くのは: コマンドを実行できないAIアプリから使うとき、開いているエディタとAIをつなぐとき（いま再生中のゲームの状態を読む、人の画面で選択する等）、呼び出しをより確実・短くしたいとき
- 方針: CLIを主とし、MCPはCLIの関数を包む薄い層として、依存ゼロで後から作る（PLAN.md の現在地）

## 2026-11-08 行列パラメータとロックの非表示

- **パラメータに2次元行列（matrix）を定義できるようにする。** インスペクタに直接並べると見にくいので、大きさだけを表示し、別ウインドウ（行列タブ、または別のブラウザウインドウ）で確認・編集する（開発者の決定）
- **ロックしたパラメータをエディタ上で非表示にできるようにする。** AI開発ではパラメータが多くなるため（開発者の決定）。「🔒を隠す」の設定は人ごとにブラウザに記憶し、共有しない（人によって見たいものが違うため）
- 実装の決定: AIはセル単位で変更する（`setCells`、CLIでは `住所[行,列]`）。行列全体を送り直すとトークンが無駄になるため。★とロックは行列全体の単位。ログは1セル1行で残し、要約では行列ごとに「Nセル変更」とまとめる
- 実装の決定: 行列エディタは表計算ソフトからの貼り付けに対応。企画担当が表計算ソフトで作った表をそのまま持ち込めるようにするため

## 2026-11-08（段階1）

### 方針・要件（開発者の決定）
- **名前は AGES**（All Games should be Edited Speedy）。理念は「とにかくゲーム開発のスピードを上げる」
- **AIが操作しやすいゲームエンジンを作る。** 長期的にはUnityに匹敵するものを目指し、時間はかかってよい。AIの扱いやすさで勝負し、機能は段階的に足す
- **最重要の2指標は「思考時間の短縮」と「トークンの節約」。** エディタの存在価値に直結する
- **人がファイルの追加・編集、パラメータの編集をできること**、**エディタウインドウを自由に設定できること**（開発者が以前のプロジェクトで使っていたように）は必須
- **人の編集はすべて記録し、AIが読めるようにする。記録はテキストのログで取る**（動画ではない。AIが安く正確に読めるため）
- **複数の編集者がいる場合はバージョン管理をする。エディタからGitHubへプル・プッシュできるようにする**
- **パラメータごとに、AIが「必ず」操作できないロックを設定できるようにする。** 人からAIに頼めることが大きく増えるため
- **MCPは必要に応じて作っていく**
- **オープンソースとして公開する。** リポジトリは公開のままでよい。ライセンスは MIT（上の項目）

### 技術（実装時の決定と理由）
- **実行時の外部依存ゼロ。** 待ち時間と壊れる箇所を減らすため。結果として、開発環境でnpmのパッケージ置き場に接続できなくても動く
- **TypeScriptを、Node 22.18以降の型除去機能でそのまま実行する。** コンパイル待ちをなくすため。型は「消すだけで動く書き方」（erasableSyntaxOnly）に限る。enum や、コンストラクタ引数でのプロパティ宣言は使わない
- **ブラウザへはエディタのサーバーがその場で型を除去して配る**（`node:module` の `stripTypeScriptTypes`）。位置がずれないのでエラーの行番号がそのまま使える
- **型チェックは任意**（`npm install` 後に `npm run check`）。実行には不要
- **正本はJSON。1行1項目で整形する。** Gitの行単位の統合が、ほぼ値単位の統合になる
- **値のアドレスは `シーン#ID.コンポーネント.フィールド`、プレハブは `@名前.コンポーネント.フィールド`**
- **更新は固定間隔（既定60fps）、乱数は `ctx.rng`（シード付き）。** 同じシード・同じ入力なら必ず同じ結果になり、AIが推測せずに確かめられる
- **差分編集はすべて成功するか、何も変えないか。** 中途半端な状態を作らない
- **人の調整（★）とロック（🔒）は別の強さにする。** ★はAIが人に確認したうえで `--force` で変えられる。🔒は `--force` でも不可で、設定・解除は人だけ
- **ロックは値も一緒に保存する**（`.ages/locks.json`）。AIがファイルを直接書き換えても、エディタは即座に、CLIは次の読み込み時に元へ戻す
- **ゲームコードの `import ... from 'ages'` は、Nodeではモジュール解決のフック、ブラウザではインポートマップでエンジンへ向ける。** プロジェクトをどのフォルダに置いても動くようにするため
- **エディタのサーバーはゲームコードを作業スレッドで読み込み、コードが変わったらスレッドごと作り直す。** モジュールのキャッシュを確実に捨てるため
- **外部からの編集（別のエディタやAIの直接編集）も検出して記録する。** ただしCLI経由ですでに記録された変更は二重に記録しない
- **AIの既読位置（`.ages/ai-cursor`）はGitで共有しない。** 操作ログ・★・🔒・レイアウトは共有する
- **AI向けの出力は日本語の短いテキスト**（JSONより少ないトークンで済むため）

### 会話の中で確認した見立て
- 小規模な2Dでは、素のHTMLはエンジンより速い。AGESの優位は規模が大きくなるほど出る。最初は同等か素のHTMLがやや有利のはず（AIがAGESのAPIを知らないため）→ ベンチマークで確かめる
- Slay the Spire くらいの規模なら、段階2まで作れば十分に優位を取れる見込み（データ中心・ターン制・画面なしで大量に試せる・描画が軽い）
- 既存エンジンが強い領域（コンシューマー機・重い3D・大規模チーム）は当面狙わない
- 「HTMLで作り、必要なら最後にAIがエンジンへ移植する」使い方を想定する
