## 2. 背景

- AIでゲームが溢れる時代になり、作る行為そのものでは差がつきにくくなった。差がつくのは「何が面白いかを見極めて、速く形にすること」
- AIと一緒に素のHTMLでゲームを作ると、コンパイルやエンジンのリフレッシュが要らず圧倒的にスムーズ。小規模な2Dなら、エンジンより速度も品質も上がることが多い
- 一方で素のHTMLは、規模が大きくなるとAIが読む範囲が広がり、パラメータ調整・チーム作業・エディタの便利さが失われる
- 既存エンジン（Unity・Unreal）は「AIが操作しやすいエンジン」へ舵を切り始めている（MCP対応、AIジャムの開催）。ただし後付けである
- 既存エンジンが強いまま残る領域: コンシューマー機、重い3D、大規模チーム。AGESは当面そこを狙わない

## 3. 対象

- AIと一緒にゲームを作る個人・小規模チーム（まずは開発者自身）
- 最初の主戦場: **2Dで、データが多く、調整の往復が多いゲーム**（シューティング、デッキ構築型ローグライクなど）
- 目標の規模感: Slay the Spire くらいの規模で、素のHTML・既存エンジンより明確に速いこと（段階2で達成）

## 4. 段階的な計画

各段階で「実際にゲームが作れる状態」を保つ。完了条件を満たしたら次へ。

### 段階1: 核・CLI・最小エディタ ✅（PR #1）
- 固定更新・シード付き乱数・入力の記録と再生・状態のハッシュ
- コンポーネントの宣言（型・範囲・説明）、検証と「もしかして」エラー
- 差分編集、操作ログ、★人の調整の保護、🔒値ごとのロック（エディタで非表示にもできる）
- 2次元行列のパラメータと行列エディタ（表計算ソフトからの貼り付け、別ウインドウ表示、セル単位の変更）
- CLI: init / map / schema / get / set / patch / run / log / check
- `ages init` と エディタ計画書（EDITOR-PLAN.md）: ゲームの企画を受けたら、まず必要なエディタを使用者と決める
- エディタ: 階層・プロジェクト・インスペクタ・ゲーム・テキスト・ログ・Git、タブの移動、再生と実行中の変更の保存、入力の記録、カスタムウインドウ、外部編集の検出とロックの復元
- 完了条件: テストと型チェックが通り、人の編集→ロック→AIの拒否→直接編集の復元→再生→カスタムウインドウが通しで動く（達成）

### 段階2: 2Dのコア（あまねくゲームを作るのに最低限の要素）

**方針（開発者の決定）**: 段階2は「どのゲームでもほぼ必ず要るもの」だけをAGES本体に入れる。題材のゲームは一例であり、そのゲームに必要なものをすべて本体に盛り込まない。2Dのみ。
特定のゲームにしか要らないもの（例: 命令の列のタイムライン）は、本体の外の「追加部品」にする。テストに必要な追加部品は作るが、本体とは分ける。

**ゲームを動かすための要素**
| 要素 | 内容 |
| --- | --- |
| 描画 | WebGL2。画像・スプライトシート・アニメーション、図形・文字、描画の順番（レイヤー）、色・透明度・合成方法 |
| カメラ | 位置・拡大・回転・追従・揺れ、画面の大きさへの合わせ方、複数のカメラ |
| 音 | 効果音・BGM（ループ・フェード）、音量の区分、同時に鳴らす数 |
| 入力 | キーボード・マウス・タッチ・ゲームパッドを「操作の名前」で扱い、割り当てを変えられる |
| シーン | 画面の切り替え、画像・音の事前読み込み |
| データの型 | リスト・構造体・どれか1つ（種類によって中身が変わる）。リストに何を入れるかは、企画を受けたAIがエディタ計画書で決める |
| 演出の基本 | トゥイーン（値を時間で変える）とパーティクル |
| シェーダー | 画面全体の後処理と、画像ごとの効果 |
| UIの土台 | 文字・ボタン・リスト・ゲージ・ダイアログ、画面に合わせた配置 |
| 当たり判定の土台 | 円・矩形の判定と範囲の検索（物理演算は本体に入れない。必要なゲームでは、AGESを使うAIがプロジェクトの中で作る） |
| 時間 | 一時停止・スロー・タイマー（固定更新は段階1で済み） |
| セーブ | 進み具合と設定の保存・読み込み |
| 多言語 | 文字を表から引く仕組み |

**作るための要素（エディタ）**
| 要素 | 内容 |
| --- | --- |
| クリックでの選択 | シーン上のオブジェクトをクリックするだけで選べる。重なっていれば、同じ場所をもう一度クリックすると奥のものへ |
| アセットの取り込みと一覧 | 画像・音・フォントの取り込み、プレビュー、フォルダ分け（画像の切り方の画面は段階2-1で済み） |
| 表データ | 同じ形の行がたくさん並ぶデータ（武器・敵・アイテムなど）と表のエディタ、表計算ソフトとの行き来 |
| 元に戻す／やり直し | すべての編集が対象。操作ログを土台にする |
| プレハブの派生 | 元を受け継いで一部だけ変える |
| 試しの窓 | 選んだものをその場で再生して確かめる |
| シーンの編集操作 | 拡大縮小・移動・格子への吸着・複数選択 |
| エディタ拡張の API | 独自のウインドウが使う窓口（パネル・インスペクタの欄の見せ方・右クリックのメニュー・ゲームの画面への描き込み・通知）。拡張性は狭めない（隔離しない）。作る前に開発者と設計を相談する |

**作る順番**（2026-11-08 に4と7を入れ替え）: 1 描画（WebGL2） → 2 カメラ → 3 音 → 4 データの型と表 → 5 入力 → 6 アセット → 7 シーン → 8 元に戻す → 9 演出 → 10 シェーダー → 11 UI → 12 当たり判定 → 13 セーブ → 14 多言語 → 15 残りのエディタ機能（派生・試しの窓・シーンの編集操作・エディタ拡張の API）。2026-11-09: シーンの後にロックマネージャーを入れる

**追加部品（本体の外。必要なゲームだけが使う）**: 命令の列とタイムライン、会話（ノベル風の窓）、タイルマップ、経路探索、状態遷移、格子マップ、自動プレイヤーによる大量シミュレーション、効果の記述ルール（カードゲーム向け）

- 完了条件: コアの要素がそろい、ベンチマークの題材の1ステージ分を（必要な追加部品と合わせて）移植して、同じ5作業で素のHTMLと比べられる

### 移植について
HTMLで速く作り、必要なら最後にAIがUnityなどへ移植する、という使い方も想定する。
そのためロジックと描画を分け、データはJSON、更新は固定間隔、入力は記録・再生できるようにしてある。
2Dで性能が足りるなら、移植せずにTauriで包んで販売する方が手間もずれも少ない。

## 5. ベンチマーク（理念の2指標を測る）

- 標準作業を決める（例: 敵を1種類追加する／パラメータを調整して難易度を下げる／バグを1つ直す／新しい攻撃パターンを足す）
- 作業ごとに **トークン数** と **所要時間**、**往復回数** を記録する
- 比較対象: ①素のHTML ②Unity＋MCP ③AGES
- 題材: 開発者の非公開の実プロジェクト（2Dシューティング、約2.3万行）。中身は非公開の作業場に置き、AGESには方法と数字だけを載せる
- 結果: [BENCHMARK.md](BENCHMARK.md)。素のHTML版の基準値は、5作業すべて成功・正味の合計 約17万トークン（2026-11-08）
- 見込み: ジャム規模では同等〜素のHTMLがやや有利（AIが新しいAPIを知らないため）。数千行を超え、調整の往復が増え、編集者が複数になるほどAGESが有利になるはず。これを数字で確かめる
- 参考値（段階1のサンプル）: 地図 約2.4KB で、全ファイル 約10.5KB を読むのと同じ全体像がつかめる
